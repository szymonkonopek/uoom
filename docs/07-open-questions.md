# Open questions

Most of what was on this list is now answered — the SDK is public
(`github.com/UNAWatch/una-sdk`), and reading it settled six of the ten
questions and reversed two of them. What the source said is in
`docs/reference/una-sdk-verified.md`; what is left needs a wrist.

---

## Still open

### 1. ~~How much RAM will the loader give an app?~~ — **measured, and worked around**

Between **878 KB and 1 009 KB per app image**, measured with the ballast probes
in `tools/probe-loader.sh`. And the ceiling is per *image*, not per app: 512 KB
of ballast in each of the two processes -- 1 147 KB combined -- runs, while
1 009 KB in one process does not.

Which is why the zone lives in the service process. The game runs.

Original reasoning:

Hardware settled half of it the hard way: **the kernel's heap cannot supply
640 KB**, so the zone cannot live in `malloc` and is a static array in the
app's own region again. That region is a link-time ceiling with no cap, so the
question is purely what the loader will hand out.

Original reasoning:

**Narrowed, not closed.** `UNA_APP_GUI_RAM_LENGTH` turns out to be a **linker
ceiling only** — the `.uapp` header records real section sizes and the loader
allocates from those, so raising the number costs nothing at run time, and
nothing in the SDK validates or caps it. Better still, `malloc` forwards to the
kernel's allocator, whose heap is **outside** the app's region entirely, so
DOOM's zone does not compete with its code at all (and UOOM now allocates it
there).

What remains unknown is the size of that kernel heap and the largest region the
app loader will carve — neither is in the SDK, because the firmware is not.

**Experiment.** Send `SDK::Message::RequestMemoryInfo` on the watch: it reports
`totalHeap`, `freeHeap`, `usedHeap`, `largestFreeBlock` and `fragmentation`.
That single message answers the port's central question. UOOM should log it at
startup — it is a five-line addition to `uoom_una_platform.cpp` and it turns a
guess into a number.

The other half of the budget is now the app region itself, because **apps
execute from SRAM**: there is no flash region in the linker script, so DOOM's
`.text` and its `const` trig tables count against `RAM_LENGTH` exactly like
`.bss`. Read it off the map file the build already emits.

### 2. ~~Is 10 Hz really the rate?~~ — **measured on hardware: 10.0 Hz**

The smoke build counted 20 ticks against the clock on the device and reported
**10.0 Hz**. `SDK::GUI::Config::kFrameRate` was right; the TouchGFX port
document's "typically 30-60 FPS" is stale prose. What remains open is only
whether the kernel *can* be asked for more -- the panel itself does 30 Hz.

Original reasoning, kept because the consequences still stand:

**The rate is settled: 10 Hz.** `SDK::GUI::Config::kFrameRate` is a real
constant with a doc comment, every example app derives its timings from it, and
the simulators pin vsync to it. The "30-60 FPS" figure in the TouchGFX port
document is stale prose that no code uses.

The panel itself does 30 Hz (Sharp's datasheet: 30 typical, 33 max, ~25 ms of
data time per frame), so **10 Hz is a kernel choice, not a hardware limit** —
`EVENT_GUI_TICK` is generated by firmware that is not in the SDK.

**Why it matters.** DOOM's logic runs at 35 tics/s. At 10 display updates a
second the port must decide how many tics to run per frame — and UOOM's input
timings (`UOOM_TAP_MS`, `UOOM_PULSE_MS`, `UOOM_WEAPON_HOLD_MS`) are tuned around a
~50 ms frame, not a 100 ms one. All three are one `#define`.

**Experiment.** Build with `-DUOOM_HUD_DIAG=1`; the frame time appears in the
corner. Then ask whether the tick can be raised, because 30 Hz would be a
different game.

### 3. ~~Do PRESS/RELEASE codes arrive?~~ — **yes, all three, in order**

On hardware, one press of the bottom-left button produced `w`, `2`, `s`: press,
click, release. So hold-based movement works, the SW3 = L2 mapping is right,
and the click-only fallback will correctly disable itself the moment it sees a
press. What is still unmeasured is the *rate* under fast play.

Original reasoning:

Unchanged, and still the thing that decides whether the control scheme works.
The codes exist in `SDK/GUI/Button.hpp` (`q/w/e/r` press, `a/s/d/f` release),
but the port docs say buttons are "processed through a 50-60ms debounce filter
and react only upon release". At a 10 Hz tick, one physical press expanding to
three codes is already most of a frame's budget.

**Already handled either way.** A `CLICK` becomes a synthetic press plus a
release 260 ms later, but only until a real `PRESS` has been seen — after which
clicks are ignored so one press is never counted twice. Self-correcting, no
build flag, both branches covered by `tests/run.sh`.

The source turned up one code the docs never mentioned: **`L1R2 = 'z'`**, a
built-in chord. UOOM expands it into both buttons, because if the firmware sends
it *instead of* the individual codes, dropping it would eat a turn or a shot in
the middle of combat.

### 4. The screen is round. What happens to the status bar?

The panel is addressed as 240x240 but lights only a **circle of radius 120** —
Sharp's per-line tables are explicit (row 240 is "109 dummy / 22 active / 109
dummy"), and at row 230 barely 96 of 240 columns are visible.

The 3D view survives it; clipped corners read as vignetting. The status bar does
not: in FILL mode it sits exactly where the circle narrows, and the ammo count
and arms panel fall off the glass.

`UOOM_SCALE_MODE=UOOM_SCALE_INSCRIBED` renders the whole frame into a 169x169
centred square so nothing is ever clipped — correct, and costs half the screen.
**The better answer is probably to stop drawing DOOM's 320-pixel status bar at
all** and put a compact health/ammo readout inside the safe area with the port's
own text renderer. That is a real change, and it wants a play test first.

### 5. ~~Can an app own the GUI task?~~ — **yes**

`UOOM first tick received` on hardware, with `UNA_SDK_SOURCES_GUI` unlinked, our
own `main()`, and no TouchGFX screen registered anywhere. This was the risk
ranked #1 and it is gone.

### 6. Colour on real glass

Mostly resolved on paper: the panel is natively **64-colour** (two bits per
subpixel by spatial area gradation), and ABGR2222's four levels per channel line
up with it exactly, so nothing is quantised twice. The bit layout is confirmed
against TouchGFX's own `LCD8bpp_ABGR2222.hpp`.

What is left is a taste question no datasheet answers: whether the 2x2 ordered
dither shimmers in motion on a reflective memory-in-pixel panel at 10 Hz.
`-DUOOM_DITHER=0` is the comparison; the host renders in `docs/04-video.md`
show what is at stake.

### 7. Which effect should gunfire feel like?

`RequestVibroPlay` is real and reachable straight from the GUI process, with the
DRV2605's effect library — `SHARP_TICK_1_100`, `STRONG_CLICK_100`,
`DOUBLE_CLICK_100`, up to eight notes per message. UOOM currently fires a sharp
tick on the shotgun. Which effect actually feels like a gun is not something to
decide from a header.

## Resolved by reading the source

Kept short; the detail and the quotes are in
`docs/reference/una-sdk-verified.md`.

| Was | Answer |
|---|---|
| **Does `IFile` have a seek?** | **Yes** — `bool seek(size_t)`, absolute only, plus `size`, `getPosition`, `truncate`, `flush`. But `read`/`write` return `bool` with an out-param, not a count, so the adapter was wrong in a way that would not have compiled. The reopen-and-skip fallback is deleted. |
| **Can an app own the GUI task?** | **Yes, by not linking `UNA_SDK_SOURCES_GUI` at all** — that group owns `main` *and* the `touchgfx_*` entry points, and does not even compile without a TouchGFX Designer project. UOOM supplies its own `main()` and borrows `TouchGFXCommandProcessor.cpp` by path, which turns out to include no TouchGFX headers and to carry the entire kernel protocol. |
| **`SDK::Kernel` member names** | `sys`, `log`, `mem`, `comm`, `fs`. The GUI provider hands back a **`const&`**. |
| **Is `malloc` usable, and where does it live?** | Yes, and it is the kernel's allocator via `IAppMemory`, **outside `RAM_LENGTH`**. `_sbrk` is a hard trap. So the zone belongs on the heap, not in `.bss` — the opposite of the usual advice, and UOOM was doing it the wrong way round. |
| **What does `RAM_LENGTH` control?** | A single MEMORY region containing `.text`, `.rodata`, `.data`, `.bss` and `.stack`. **No flash region — apps run from SRAM.** And it is a ceiling, not a reservation. |
| **Which libc is available?** | Not the toolchain's: `libc.a`, `libm.a` **and `libgcc.a`** are `/DISCARD/`ed, and 336 symbols are bound to addresses in the kernel's newlib. Missing and needed: `strcasecmp`, `strncasecmp`, `abs`, `atoi`, `puts`, `putchar` — **and every `__aeabi_*` helper**, which makes `FixedDiv`'s 64-bit division a link error in the renderer's hot path. `uoom_libc.c` and patch 0011 exist for this. |
| **The frame tick** | 10 Hz (see #2). |
| **Backlight fields** | `brightness` is a **percentage**, and `autoOffTimeoutMs = 0` **disables** auto-off — so arm it once at startup rather than re-arming forever. |
| **Haptics message** | `RequestVibroPlay`, reachable from the GUI process directly. No service round-trip. |
| **Message pool sizes** | Static asserts in the headers give exact sizes (`RequestBacklightSet` 40 B, `RequestVibroPlay` 100 B, `RequestBuzzerPlay` 116 B). UOOM's own messages are tiny. |
| **`syscalls.cpp`** | Does not exist; `system.cpp` plays that role, and `_write` is **not** implemented — `printf` to a console is unusable, logging goes through `kernel.log`. |

## One trap worth repeating

`app_packer.py` copies exactly nine known ELF section names and merely *warns*
about anything else. A custom `__attribute__((section(...)))` builds clean and
arrives on the watch as garbage. UOOM had one; it is gone.
